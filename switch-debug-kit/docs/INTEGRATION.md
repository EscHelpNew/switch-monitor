# Подключение к своей игре

## Что перенести

Скопируйте `receiver/`, `host/`, `project.example.json`, `build.py` и при необходимости `lab/`. Можно проще скопировать всю папку комплекта. Настройте собственный `project.json` и выполните:

```powershell
python build.py --config-only
```

Скомпилируйте **шесть** единиц: `reload_core.c`, `reload_bridge.c`, `remote_reload.c`, `reload_launch.c`, `reload_reports.c`, `reload_main.c`. Добавьте include-пути `receiver/` и `build/config/`; используйте C11, SDK libnx, поддержку потоков и сокетов. Сборка игры уже должна использовать стандартный Switch toolchain и линковать libnx. Пример CMake:

```cmake
set(NXDK_CONFIG_DIR "/absolute/path/to/switch-debug-kit/build/config")
add_subdirectory("/absolute/path/to/switch-debug-kit/receiver" kit_receiver)
target_link_libraries(your_game PRIVATE switch_debug_receiver nx)
```

API `game_reload_*`, wire-target `GAME`, marker `GAME_REMOTE_RELOAD_BRIDGE_V2` и magic `APPRLD2` относятся к протоколу 2. Конфиг задаёт собственные ID, имя и пути игры или приложения. Клиент, приёмник и мост нужно обновлять вместе; протокол 1 несовместим с этой версией. После перехода заново выполните bootstrap.

## Старт приложения

Посмотрите собираемый [receiver_main.c](../examples/receiver_main.c). В своей точке входа порядок такой:

```c
if (game_reload_early_bridge()) return 0;
game_reload_configure(argc, argv);       /* Именно основной поток. */
/* Инициализация сети, если игра ещё не сделала это. Не инициализировать дважды. */
if (R_SUCCEEDED(socketInitializeDefault())) {
    nxlinkStdioForDebug();               /* stdout остаётся консолью, если нужен. */
    game_reload_start(NXDK_APP_NAME, "1.0.0");
}
```

`early_bridge` должен выполняться **до** игровых потоков, графики, аудио, JIT и специальных отображений памяти. Только на этом раннем пути разрешён возврат в homebrew loader: он проверяет packet и digest, делает `envSetNextLoad`, затем `main` возвращает 0. Нельзя вызвать его посреди работающей игры.

Если игра использует UserChannel для собственных параметров запуска, после нулевого результата early_bridge заберите исходный объект через `reload_user_channel.h`:

```c
AppletStorage ordinary = {0};
if (game_reload_take_user_channel(&ordinary)) {
    /* Прочитать данные штатным парсером игры через appletStorageRead. */
    appletStorageClose(&ordinary);
}
```

Мост закрывает только распознанный kit-пакет; чужие данные не копируются в ограниченный буфер и не выбрасываются. После take владение переходит игре. Не пытайтесь вместо этого повторно pop тот же объект из системного канала: мост уже сохранил его. Если параметры игре не нужны, явно закройте полученный объект, как сделано в примере и стенде. Вызывайте early_bridge один раз; перед его проверкой не потребляйте UserChannel в другом стартовом коде.

`configure` запоминает владельца основного потока. `start` запускает приёмник только с валидным явным токеном. Имя передавайте `NXDK_APP_NAME`; версию — короткой константой из цифр/букв/точек/дефиса, без управляющих символов и кавычек. Переданный NRO не должен содержать ключ в исходниках или rodata.

Собственный парсер аргументов игры должен пропускать служебные `--token=`, `--game-remote=`, `--game-log-host=` и `--game-reload-image=` после configure, не печатая их значения. Configure читает их, но не перестраивает argc/argv игры. Публичные заголовки поддерживают C++ через extern C; SDK-зависимый заголовок UserChannel подключайте в платформенной части, где допустим libnx.

## Главное меню и ожидание игры

Пока главный поток выполняет своё меню/цикл, регулярно вызывайте `game_reload_main_poll()` из него. Сетевой поток только ставит запрос и ждёт результата; он не вызывает системный запуск, не освобождает игру и не возвращает управление загрузчику.

Если вся игра работает в отдельном GAME-потоке, основной поток должен ждать так:

```c
static void *game_entry(void *arg) {
    void *result = your_game_main(arg);
    game_reload_game_done();
    return result;
}

/* После успешного pthread_create: */
game_reload_wait_game();
pthread_join(game_thread, NULL);
game_reload_main_finish();
```

Это замена блокирующего `pthread_join` в основном потоке: ожидание по событиям принимает запросы запуска, не добавляя таймерного опроса и работы в подготовку кадра. Не запускайте отдельный поток, который вместо main вызывает `main_poll` — проверка владельца отклонит его.

Если игровой цикл сам живёт в main, вызывайте poll в безопасной точке его итерации. Учтите длительные блокирующие загрузки: пока main не возвращается к poll, RUN не выполняется. Не пытайтесь обходить это запуском SDK-команд в network worker.

## Все пути выхода

Перед **любой** очисткой и возвратом из main, после которого уже могли появиться потоки приёмника, вызывайте `game_reload_main_finish()`. В том числе при отмене меню, ошибке boot и ошибке создания GAME-потока. При работающем приёмнике finish завершает процесс через систему и не возвращается загрузчику даже при ошибке IPC. Без приёмника функция возвращает сразу.

Если другие собственные фоновые потоки тоже имеют время жизни процесса и могут пережить main, отметьте это через `game_reload_main_resident()` после их успешного старта. Иначе реализуйте их полную остановку/снятие callback/join до обычного loader return. Это обязанность интегрирующей игры, а не универсальная остановка всех возможных потоков.

Одновременный пользовательский выход и RUN может завершить приложение раньше исполнения RUN. Клиент обязан требовать нового подключения, а не считать `OK RESTART_REQUESTED` доказательством успеха.

## Ярлык и файлы SD

Нужен собственный установленный forwarder, запускающий `bridge.nro` из настроенной папки. Проверяются фактический ProgramId и NACP name/author/presence_group_id. Комплект не включает установщик title и не меняет чужие приложения.

На SD:

```text
switch/<sd_directory>/
  bridge.nro       # игра с ранним мостом и тем же проектным конфигом
  game.nro         # обновляемая игра с приёмником
  arm-lab.nro      # отдельный стенд
  token.txt        # опционально для модульного сервиса при SD-запуске стенда
```

Во время передачи используются `.incoming` и `.previous`. Не смешивайте на двух концах конфиги, ABI или разные title_id. Игровые данные/сохранения располагает сама игра; протокол не получает произвольных путей к ним.

## Приёмка интеграции

1. Обычный запуск без токена не открывает TCP 28285; игра ведёт себя штатно.
2. Неверная авторизация, оборванный PUT, неправильные SHA/NRO не заменяют прежний образ.
3. Нулевой/чужой/несовпадающий installed title не вызывает Restart собственного текущего host.
4. После первого bootstrap откройте свой ярлык при необходимости передачи фокуса.
5. Запишите PID и точные digest; проверьте LAB → LAB → GAME → LAB → GAME без ручного HOME.
6. Повторите из реально работающей игровой сцены с аудио/GPU/worker threads.
7. Пересоберите небольшой вариант, выполните deploy и убедитесь, что работает новый digest и новый процесс.
8. Проверьте отмену стартового меню и ошибки boot: loader не должен снимать NRO с живыми потоками.

Локально собранный пример не заменяет эти проверки на конкретной игре. GDB можно использовать для чтения PID/стека, но он не включается этим комплектом.
